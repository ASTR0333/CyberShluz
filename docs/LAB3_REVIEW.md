# Проверка лабораторной работы №3

## Исправления в методических командах

В исходной методичке есть команды, которые нельзя копировать буквально:

- После `hostnamectl set-hostname l-ms.cyberprotect.test` команда `newgrp` не нужна и не относится к обновлению hostname. Проверка `hostname` уже должна показать новое имя; для новой login-shell при необходимости используют `exec "$SHELL" -l`.
- `su –` содержит типографское тире. Корректная команда: `su -`.
- `firewall-cmd –-reload` содержит неверный символ тире. Корректная команда: `firewall-cmd --reload`.
- Формулировка «Регистрация с маркетом» — опечатка; речь идёт о регистрации с маркером.
- Имя `LMS` в одном из шагов не совпадает с таблицей. Для стенда используется точное FQDN `l-ms.cyberprotect.test`.

## Соответствие топологии

Значения по умолчанию в приложении приведены к PDF:

| Роль | Образ | Flavor | IP |
|---|---|---|---|
| L-MS | `LAB2_TMP_L-MS/Debian11.11` | `small` | `10.0.0.10` |
| L-NFS | `LAB2_TMP_L-NFS` | `start` | `10.0.0.70` |
| L-PGSQL | `LAB2_TMP_L-PGSQL` | `start` | `10.0.0.55` |
| W-DC | `LAB2_TMP_W-DC` | `medium` | `10.0.0.5` |
| V-HYPERV | `LAB2_TMP_V-HYPERV` | `large` | `10.0.0.65` |

До исправления код использовал `edu 2x2` для Linux и `edu 4x4` для обеих Windows-машин, поэтому потребление ресурсов и поведение стенда не соответствовали топологии.

## Что проверяется автоматически

- L-MS, L-NFS и L-PGSQL доступны по SSH; внутренние машины проверяются через L-MS как bastion.
- Hostname каждой Linux-машины точно соответствует её роли и домену `.cyberprotect.test`.
- На L-MS слушает порт веб-консоли `9877`.
- На L-NFS открыты `7780/tcp`, `9876/tcp`, `9852/tcp`, `9862/tcp`.
- На L-NFS загружен `snapapi`.
- На L-NFS запущена хотя бы одна служба Acronis/Cyber Protect.
- На L-NFS существует каталог `/BackupL`.

Старый алгоритм фактически передавал Ansible только Floating IP L-MS. Условия для L-NFS пропускались, но итог мог стать `PASSED`. Этот ложноположительный сценарий устранён.

## Что остаётся ручной проверкой

Текущих SSH/API-доступов недостаточно, чтобы доказать следующие действия:

- на W-DC запущены `Cyberprotect Storage Node Service`, `Cyberprotect Catalog Browser Service` и `Elasticsearch`;
- `w-dc.cyberprotect.test` отображается среди узлов хранения;
- в веб-консоли созданы и отображаются RepoW и RepoL.

Эти пункты показаны отдельными чекбоксами. Без подтверждения результат имеет статус `REVIEW_REQUIRED`: оценка в Moodle не отправляется, очистка стенда не запускается. Это предотвращает преждевременную выдачу 100 баллов и удаление стенда.

Ручное подтверждение является заявлением пользователя, а не техническим доказательством. Для полностью автоматической проверки потребуется документированный API Cyber Protect либо WinRM-доступ к W-DC с отдельной защищённой учётной записью.
