Безопасный веб-сервис оркестрации облачных лабораторных стендов на платформе «Кибер Инфраструктура» (OpenStack). Управление пулом изолированных сред «on-demand», сквозная интеграция с LMS Moodle по LTI 1.3, предиктивный контроль ёмкости кластера и автоматическая SSH-проверка конфигураций.

Обзор

1 · О проекте

Перенос практических лабораторных работ в облако решает проблему доступности ресурсов, но порождает вызовы: рост нагрузки на преподавателей, требование жёсткой изоляции сред, риск исчерпания ёмкости кластера и рутинную ручную проверку конфигураций. КиберШлюз — отказоустойчивый шлюз оркестрации, который:

Раздаёт ресурсы «по требованию»
Менеджер заранее подготовленного пула изолированных сред: «1 студент = 1 индивидуальный стенд».
Контролирует ёмкость КИ
Запрос лимитов Nova и блокировка запуска при утилизации > 90% с уведомлением и логом.
Интегрирован с Moodle
Сквозной сценарий по LTI 1.3: клик «Выполнить ЛР» в LMS → выделение стенда → возврат оценки (AGS).
Проверяет лабы автоматически
Безагентное SSH-подключение и расширяемый движок проверок на Ansible с детальным логом.
Ключевой принцип ИБ: сервис не создаёт домены/проекты «на лету» и не требует прав суперадминистратора. Он лишь распределяет заранее подготовленные изолированные среды и возвращает их в пул после очистки.

Жизненный цикл

3 · Машина состояний стенда

Каждый стенд проходит детерминированную машину состояний; переходы инициируются API и Celery-воркерами, а истечение TTL/заморозки — периодической задачей cleanup_expired_stands (beat).

FREE→ DEPLOYING→ READY→ CLEANING→ FREE
READY— «нужна помощь» → FREEZE (24ч)— thaw / истёк → CLEANING
СостояниеЧто означаетПереход
FREEСлот свободен в пуле.→ DEPLOYING при выделении.
DEPLOYINGИдёт создание сети и ВМ в КИ.→ READY при успехе; → FREE при ошибке (с ретраями).
READYСтенд готов, выдан публичный IP. Таймер TTL стартует здесь.→ CLEANING (истёк/завершён) или → FREEZE.
FREEZE«Техническая поддержка»: автоудаление заморожено на 24ч для аудита.→ READY (thaw) или → CLEANING.
CLEANINGУдаление ВМ и изолированной сети, возврат слота в пул.→ FREE.
Таймер времени жизни начинает отсчёт в момент готовности (READY), а не при постановке в очередь — студент не теряет время лабы на сам деплой. Время отдаётся как UTC-aware ISO, чтобы обратный отсчёт был корректным в любом часовом поясе.

Этап 1 · Безопасность

5 · Пул сред и реальная изоляция

Пул слотов хранится в PostgreSQL. Выделение — атомарное, чтобы исключить гонку при одновременных запросах: строка свободного стенда блокируется на уровне БД.

# app/core/pool_manager.py — атомарный захват свободного слота
stand = (db.query(Stand)
           .filter(Stand.status == StandStatusEnum.FREE)
           .with_for_update(skip_locked=True)   # SELECT ... FOR UPDATE SKIP LOCKED
           .first())
if not stand:
    return None            # нет свободных слотов → API отдаёт 503 с понятным текстом
stand.user_id = user.id
stand.status  = StandStatusEnum.DEPLOYING

Модель изоляции (Neutron)

На каждый стенд создаётся собственный изолированный L2/L3-сегмент — отдельная сеть Neutron, подсеть 10.10.0.0/24 и маршрутизатор с внешним шлюзом в сеть Public. Это в точности модель изоляции из ТЗ («собственные изолированные сети, объединённые с публичной сетью через маршрутизатор») и устраняет коллизию фиксированных IP топологии между параллельными стендами.

# app/core/openstack_client.py — _ensure_stand_network()
network = conn.network.create_network(name=f"stand{id}-net")
subnet  = conn.network.create_subnet(network_id=network.id, cidr="10.10.0.0/24",
                                      gateway_ip="10.10.0.1", dns_nameservers=["8.8.8.8"])
external = conn.network.find_network("Public")
router  = conn.network.create_router(name=f"stand{id}-router",
                                      external_gateway_info={"network_id": external.id})
conn.network.add_interface_to_router(router, subnet_id=subnet.id)
# Floating IP выдаётся только L-MS — единственная точка входа стенда;
# остальные ВМ доступны через неё по внутренней сети 10.10.0.0/24.

При очистке сеть, подсеть и маршрутизатор сносятся (_teardown_stand_network), возвращая ресурсы Neutron в проект.

Нативные SSH-ключи

Статические пароли в коде для доступа к стендам не используются. Пара ключей генерируется и в Nova загружается только публичная часть; приватный ключ хранится сервисом для Ansible-проверок. ВМ настраиваются через cloud-init: создаётся пользователь с ключом, sudo NOPASSWD, парольная аутентификация SSH отключается.

Особенность контура: КИ (Cyber Infrastructure 6.7) не поддерживает server-side генерацию keypair через Nova, поэтому применён документированный путь — генерация ключа на стороне сервиса и загрузка только public-части (аналог vinfra service compute key create --public-key).
Этап 1

6 · Предиктивный контроль ёмкости

Перед развёртыванием сервис запрашивает абсолютные лимиты Nova (используемые/максимальные ядра) и вычисляет прогнозируемую утилизацию. При превышении порога MAX_CLUSTER_UTILIZATION (по умолчанию 90%) запуск блокируется: пользователю возвращается 423 Locked с понятным сообщением, а отказ фиксируется в административном логе.

# Гейт в app/api/v1/deploy.py
utilization = os_client.check_capacity(required_vcpus=...)
if utilization > settings.MAX_CLUSTER_UTILIZATION:
    logger.error("[ADMIN_ALERT] деплой отклонён | util=%.1f%% | лимит=90%%", utilization*100)
    raise HTTPException(status_code=423, detail="Кластер перегружен. Попробуйте позже.")
Дорожная карта: расширение предиктива на RAM и Storage и режим «fail-closed» при недоступности Nova API (сейчас при сетевом сбое возможна мягкая деградация).
Этап 2

7 · Асинхронная архитектура

Все длительные операции (развёртывание, проверка, очистка) вынесены в Celery-воркеры — HTTP-запросы возвращаются мгновенно, UI не блокируется. Прогресс транслируется через состояние задачи и опрашивается фронтендом.

  • Идемпотентность: task_id = stand_id — повторный запуск не плодит дубли.
  • Повторные попытки: deploy_stand_task с max_retries=2 и backoff — устойчивость к транзиентным сбоям API КИ.
  • Реконсиляция: celery-beat периодически переводит истёкшие стенды в CLEANING.
  • Визуализация: фронт отображает все состояния машины и прогресс деплоя в реальном времени.

Этап 3

9 · Движок автоматической SSH-проверки

Сервис безагентно подключается к ВМ студента по SSH, используя нативные ключи, и запускает расширяемый движок проверок на базе Ansible. Плейбуки автоматически обнаруживаются по шаблону ansible/lab<NN>_*.yml, что позволяет добавлять новые лабы без правки кода.

  • Проверка наличия установленного ПО и состояния служб;
  • Валидация конфигурационных файлов под паттерн конкретной лабы;
  • Проверка открытых сетевых портов (например, Snapdrive на 9877, NFS, СУБД);
  • Детальный лог ошибок выводится в интерфейс (стилизованный терминал с итогом PASSED/FAILED).

Результат проверки сохраняется на стенде и (при интеграции с LMS) отправляется обратно в Moodle оценкой.

Этап 4

10 · Интеграция с LMS Moodle (LTI 1.3)

Реализован промышленный протокол LTI 1.3 (приоритетное/бонусное решение): Tool — оркестратор, Platform — Moodle. Сквозной сценарий:

Студент в Moodle → «Выполнить ЛР №3»
  → GET/POST /lti/login   # OIDC third-party initiation, редирект на платформу
  → POST    /lti/launch   # валидация id_token (RS256 по JWKS платформы),
                          # маппинг пользователя, сессия оркестратора
  → редирект студента в UI КиберШлюза (он сам запускает стенд)
  ... после прохождения проверки ЛР3 ...
  → AGS: client_credentials + Score → оценка возвращается в журнал Moodle
  • Подпись/проверка JWT — RS256 (PyJWT + httpx), собственный JWKS Tool отдаётся на /lti/jwks;
  • Валидация iss, aud (client_id), nonce, срока действия id_token;
  • AGS (Assignment & Grades Service) — асинхронный возврат оценки после PASSED;
  • Безошибочный маппинг: метаданные курса/пользователя LTI → персональный стенд студента.
UX

11 · Веб-терминал к стенду

Студенту не нужен локальный SSH-клиент: интерактивная сессия открывается прямо в браузере. Бэкенд проксирует WebSocket в SSH-канал (paramiko) к точке входа стенда, фронтенд рендерит терминал на xterm.js.

  • Эндпоинт WS /api/v1/stand/{id}/terminal; авторизация по JWT в query-параметре;
  • Проверка владельца: студент открывает только свой стенд, преподаватель/админ — любой;
  • Доступ к ВМ — тем же сервисным механизмом, что и bootstrap (учётные данные студенту не раскрываются);
  • Поддержка изменения размера PTY (resize) и корректное закрытие сессии.

12 · Информационная безопасность и DevSecOps

Без суперадмина
Сервис не создаёт домены/проекты «на лету» — только распределяет пул. Минимизация прав.

SSH по ключам; парольная аутентификация на ВМ отключается через cloud-init.

JWT-доступ
Ролевая модель (student/teacher/admin), проверка владельца стенда.
Non-root контейнеры
Бэкенд работает от непривилегированного пользователя.

14 · Развёртывание

cp .env.example .env        # OS_*, DB_*, JWT_SECRET_KEY, LTI_* …

# 2. Запуск всего окружения
docker compose up -d --build

# 3. Пул из 10 слотов засевается автоматически при первом старте
